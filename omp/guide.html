Using your OMP skills

Three paths, seventeen skills, one rule: the models settle what they can, you decide what matters, and nothing is built or raised until you say so.

Pick your path

Ask one question first: what are you starting from?

New app Nothing exists yet Requirements, stack, blueprint, design, then issues. Every big decision is made before any code. Feature The app runs; this adds something real New data, a new screen, a new API, auth, a new library, or a change to promised behaviour. Small change Bug fix or tweak, no decisions Straight to a plan you approve, then the code. No grill, no design step.

Not sure if it is a feature or a small change?

Use Feature if any of these is true:

  • It adds or changes stored data (a new table, field or migration).
  • It adds or changes a route, API, CLI command or config.
  • It touches sign-in, permissions or privacy.
  • It changes something docs/requirements.md promises, or users rely on.
  • It needs a library or service docs/stack.md does not have.
  • It adds a screen or changes the flow of a designed one.

None of them? It is a small change.

One-time setup

  1. Link the skills and agents

    Terminal, in the dotfiles repo
    omp/link-skills

    Rerun it after pulling changes that add or remove a skill or agent, then restart OMP.

  2. Install ponytail

    Terminal
    npx skills add DietrichGebert/ponytail -g --skill ponytail

    implement and work stop without it; it keeps every change to the smallest complete one.

  3. GitHub CLI 2.94 or later, signed in

    Terminal
    brew upgrade gh && gh auth login

    raise-issues needs it for blocked-by links; issue-branch and raise-pr need it to read issues and open PRs.

  4. Open Paper Desktop before designing

    design and review-ui draw and read through it. They never start it for you.

New app

Building a new app

You plan once, then build issue by issue. The top row runs once; the bottom row repeats for every issue.

  1. Write down what you want

    Optional, but faster: record what you already know, in your words. Nothing is researched or invented.

    You type
    /skill:draft-docs requirements A web app for book clubs. Members join by invite link, vote on the next book and RSVP to monthly meetings. Only the club owner can remove members.

  2. Grill the requirements

    Two models question and answer each other. You only get the questions that matter, as a form.

    You type
    /skill:grill-requirements

    You get docs/requirements.md with Status: Settled. How the grill works →

  3. Grill the stack

    You type
    /skill:draft-docs stack Next.js, Postgres, hosted on Vercel
/skill:grill-stack

    You get docs/stack.md: one choice (or your deferral) for runtime, framework, datastore, auth, hosting and, for a UI, the component library and styling.

  4. Read the blueprint

    You type
    /skill:blueprint

    You get docs/blueprint/: five short pages with diagrams, about 30 minutes in total. Open docs/blueprint/index.html in a browser. Ask for changes with /skill:blueprint move invites before voting.

  5. Design it in Paper

    Grey wireframes and the flow first; colour only after you approve the flow.

    You type, one at a time as each stage finishes
    /skill:design calm and dense, like Linear
/skill:design approve
/skill:design pick Quiet
/skill:design approve
    • Wireframes
    • approve →
    • Directions
    • pick →
    • Drawn
    • approve →
    • Approved

    Wireframes and the design live on separate pages of one Paper file. Directions are skipped when you gave one.

  6. Raise the issues

    You type
    /skill:raise-issues
/skill:raise-issues approve

    First call drafts docs/issues.md for you to read; nothing reaches GitHub until approve. Issues are vertical slices with blocked-by links, skeleton first.

  7. Build each issue

    You type
    /skill:issue-branch https://github.com/you/shelf/issues/3
/skill:implement https://github.com/you/shelf/issues/3 — voting lives in its own module under src/votes
approve
/skill:commit
/skill:raise-pr main

    You give the architecture in one line; implement writes a one-minute plan and waits for approve. Issues with no blocker can run in parallel worktrees.

Feature

Adding a feature

The same pipeline, cut down to one feature: a spec instead of full requirements, no blueprint, and the stack grill or design only when the feature needs them.

  1. Get on a branch

    You type
    git switch -c reading-reminders

    Or /skill:issue-branch <URL> when there is an issue. feature refuses to run on the default branch.

  2. Start the feature

    You type
    /skill:feature Email members a reminder three days before each meeting

    It reads the code it touches, then grills a spec into docs/features/reading-reminders/spec.md. Same form-based questions as the requirements grill.

  3. Run the extra step it names, if any

    Example: email is new technology
    /skill:grill-stack Resend for docs/features/reading-reminders/spec.md
/skill:feature

    Rerunning /skill:feature carries on from where the folder says.

  4. Approve the issues

    You type
    /skill:feature approve

    It raises the issues, merges the spec into docs/requirements.md and deletes the feature folder.

  5. Land the docs, then build

    You type
    /skill:commit
/skill:raise-pr main

    Then each issue goes through issue-branch → implement → commit → raise-pr.

Grills and questions

grill-requirements, grill-stack and the spec step of feature all work the same way.

  1. One model asks, another answers

    Haiku 5.5 asks; Sonnet 5.5 answers from the repo, the docs, or its own expertise. If either is unavailable, both switch to GPT 6.1 Terra and Sol.

  2. They argue once

    Each challenge gets one rebuttal and one rejoinder. Small choices become recorded defaults you can override.

  3. You get only the big questions

    A choice reaches you only if it moves scope, changes core behaviour, is costly to undo (stored data, public APIs, auth), costs money, or two of your statements conflict.

  4. A fresh pair checks it all

    Sonnet 5.5 asks and Opus 5.5 answers in a final round over the whole document. Then it is Settled.

“Not sure — decide when implementing”

Pick it when you cannot decide yet. The question is saved with your words under Open questions (requirements) or Decisions for you (stack), stops blocking, and comes back as Decide first in the issue that needs it. implement asks it in that issue's plan and records your answer.

Approvals and gates

Nothing that costs you something happens on silence. These are the only words that move things forward:

You sayWhat happens
Answer the grill formThe answer goes into the document; the next round starts.
/skill:design approveApproves the wireframes (then directions start) or the full design.
/skill:design pick <name>Chooses a drawn direction for the full design.
/skill:raise-issues approveRaises the drafted issues on GitHub.
/skill:feature approveRaises the feature's issues and folds the spec into the requirements.
approve after an implement planBuilds exactly that plan.

What blocks what

  • blueprint, design and raise-issues refuse to start until requirements and stack both say Status: Settled.
  • design needs the blueprint for a new app.
  • raise-issues needs the design Approved for any screen in scope.
  • implement changes nothing but its plan until you approve.

When something stops

You seeDo this
not ready: … not SettledRerun the grill it names; it resumes from the file and shows what is under Unresolved.
The final round stopped (model unavailable)/skill:grill-requirements final, /skill:grill-stack final or /skill:feature final.
An agent or skill is missingRun omp/link-skills in the dotfiles repo, then restart OMP.
Paper is not runningOpen Paper Desktop; design keeps writing docs/design.md meanwhile.
Changed your mind after approvingSay the change: /skill:design <change>, /skill:blueprint <change> or /skill:feature <change>. Each redoes only what the change touches.
Source of truth: each omp/skills/<name>/SKILL.md. This page summarises them; when they disagree, the skill wins.
